# Audit checks

After every cross-validated plan, Holdout audits its own pipeline on the **development rows
only**. Each check returns typed flags (evidence, a plain-language message, a typed fix);
`report.md` shows them as a table and `audit.json` holds the full evidence. A critical flag,
an incomplete audit or a contaminated holdout blocks unsealing (see
[design.md](design.md#the-audit-layer-week-2)).

All thresholds are in `src/holdout/audit/thresholds.toml`. They are **frozen** for the
Week 4 benchmark after one review on the development suite only, which left every value
unchanged (see [design.md](design.md#one-time-tuning-week-4)). Lift is measured against the dummy
baseline; "normalized" means the share of the way from dummy to a perfect score, which makes
rules metric-independent.

| Check | Detects | Method | Severity | Fix | Known blind spots |
|---|---|---|---|---|---|
| **A1** single-feature leakage | one column that alone does (almost) the whole job | depth-3 tree on each feature alone, cross-validated with the run's own splitter (categoricals target-encoded inside each fold); relative lift = (single - dummy) / (full - dummy) | warning if normalized >= 0.95, or relative lift >= 0.8 when the plan is at least halfway to perfect; **critical only if corroborated by A2 or A3**; info if the plan already drops the column | drop the column | Cannot tell an honest near-perfect predictor (mushroom odor) from a leak without corroboration, so an uncorroborated leak stays a warning. A train/validation lift gap is **not** used as corroboration: a real leak generalises within dev CV and shows no gap; a gap means memorisation (A3's job). Misses weaker single-column leaks in data where the full plan is not strong. Interactions (a leak split across two columns) are invisible to a one-column test. |
| **A2** post-outcome hints | columns recorded after the outcome | `HintProvider` protocol; offline `LexiconHintProvider` matches outcome-timing words (refund, cancel, settled, final, ...), tokens shared with the target name or goal, and post-outcome status values; in agent runs `GeminiHintProvider` (column names, up to 5 sample values, the goal) is merged with the lexicon's hints | info by default; warning when the column also has signal (A1 normalized >= 0.10); never critical alone; upgrades A1 to critical | drop the column | A lexicon only knows English words it lists; abbreviations ("rfnd_flg") and domain jargon are missed offline; the Gemini provider can read them but may also suggest false hints, which A2's signal gate keeps at info. Generic shared tokens can cause info-level noise. |
| **A3** ID-like with signal | identifiers issued in an outcome-related order | integer or string columns that are near-unique (or profiled as IDs); supporting signals: gap-free integer sequence (allowing the holdout's share of gaps), uniform code shape, correlation with row order; signal from A1 | critical if it has signal (normalized >= 0.10) and the plan uses it; warning if the plan drops it; info without signal | drop the column | Continuous floats are never treated as IDs. IDs that repeat (entity keys) are A5's job. An ID whose signal is only non-monotonic (e.g. a hash prefix) is caught only if a depth-3 tree on the number finds it. |
| **A4** duplicates | identical feature rows across folds, within dev, or across the seal | normalised feature-row fingerprints (floats to 6 significant digits, strings stripped and lower-cased; label excluded); per fold, validation rows whose duplicate is in training; holdout overlap via the seal's counts-only API | share >= 1% (cross-fold or holdout) is critical; holdout overlap >= 1% also **invalidates the holdout**; any smaller positive share is a warning with the count | deduplicate (before splitting, then a new run, when the holdout is affected) | Near-duplicates are caught only below 6-significant-digit differences. Low-cardinality all-categorical data has natural duplicates; the 1% share rule keeps that from being an alarm, but such data can still exceed it legitimately. |
| **A5** group leakage | the plan memorises entities (customers, patients) | entity candidates from structure alone (repeats, 20+ values, entity-constant columns or a string key; datetime columns excluded); plan CV with the run's splitter vs GroupKFold on the same rows; noise from re-running the reference with another shuffle | critical if the drop is >= 20% of the claimed lift **and** >= 3x the noise: also **invalidates the holdout**; warning from 15%; with `--entities known`: info citing the declaration, never invalidates | new run with `--split group:COL --entities new` (or declare `--entities known`) | A numeric entity key with no entity-constant columns is not tested. Unseen categories under GroupKFold can lower the score for reasons other than memorisation (mitigated by the entity-structure requirement). Skipped for time splits. |
| **A6** time leakage | the score depends on training on the future | orders from datetime-parseable columns (any name), integer monotonic columns, and the row order when the target is autocorrelated beyond a shuffled baseline (z >= 4); **sort confound**: if an ordinary feature explains the row order, warning only; plan CV with forward-chaining folds vs the same folds on a shuffled order (size-matched), noise from a second shuffle | critical if the drop is >= 20% of the claimed lift **and** >= 3x the noise: also **invalidates the holdout**; warning from 15%; sorted-by-feature: warning, never invalidates | new run with `--split time:COL`; if time is only in the row order, add a row-number column first | If the date was removed and no feature drifts with time, a random split cannot exploit time either, so nothing is flagged (correctly for leakage, but drift itself is not reported). A file sorted by a feature that is also chronological is reported as a sort warning, not a time critical. Skipped for time splits. **A smooth trend in the target along the row order is nearly invisible to the lag-1 gate**: on the dev suite's semi-synthetic `time_order` trap (positive rate rising from about 24% to 45% across the rows), z was 0.65 and 1.21, and even with the gate forced open the forward-chaining drop was only 7%. |
| **A7** metric fit | metrics that cannot separate a model from a trivial guess | wraps `validate_plan` metric issues (no duplicated logic); for accuracy on an imbalanced target, computes balanced accuracy and (binary) PR AUC for plan and dummy as secondary CV metrics; regression: R2 on a heavy-tailed target ((p99 - p50) / IQR >= 10) | accuracy on a minority < 20%: critical; heavy-tailed R2: warning | use balanced accuracy (or PR AUC); use MAE | Only the listed metric pitfalls; it does not judge whether the metric matches the business cost. |
| **A8** format issues | numbers as text, spelling variants, missing-value codes | parse after removing currency tokens, thousands separators, percent and unit suffixes (>= 90% must parse and some must need cleaning); values that collapse when stripped and lower-cased; sentinels (-999, 9999, -1, ...) covering >= 0.5% of rows and >= 3 IQRs from the median | warning (never critical: quality, not leakage) | exact action: parse with listed tokens / mapping of variants / treat value as missing | -1 or 0 inside a column's normal range is not flagged (ambiguous). Locale formats ("1.200,50") and dates stored as text are out of scope. |
| **A9** encoding leakage | target statistics computed on the rows they encode | inspects the **compiled** pipeline: `TargetEncoder` with `cv >= 2` is cross-fitted; target-free encoders are ignored; any other target-aware encoder is unsafe until classified | info "prevented by construction" when target encoding is used; critical if an unsafe encoder appears | use `target_cv` | Relies on a list of known encoder classes; a test fails if the schema gains an encoding that is not classified. |
| **A10** too good to be true | near-ceiling scores | normalized plan score >= 0.95 switches the audit to **deep mode** (A1 on every feature without row sampling up to 50k rows / 1000 features; A5 and A6 test up to 6 and 4 candidates) | info only; never a flag on its own | none (deep mode is the response) | A near-ceiling score with an honest cause still costs a deeper audit; a leak that only lifts a mediocre score does not trigger deep mode. |
| **A11** causal claims | causal language a predictive model cannot support | phrase lexicon (causes, leads to, drives, results in, effect of X on Y, because of) per sentence, skipping negated uses ("does not cause"); structured claims flagged directly | warning | remove the claim | In agent runs A11 checks the generated report (text and its `causal_claim` field); a claim the model will not remove is stripped by code and recorded as a substitution. Offline runs and `holdout run` record A11 as *skipped* (not a failure), since they write no prose. Paraphrases outside the lexicon ("is responsible for") are missed; negation handling is a 4-word window. |
| **A12** unstable validation | fold spread that could change the conclusion "the plan beats the dummy" | the plan and the dummy are cross-validated on the same seeded folds, so their per-fold differences are paired; the 95% interval of the mean difference uses the **Nadeau-Bengio corrected resampled t-test** (Nadeau & Bengio, *Inference for the Generalization Error*, Machine Learning 52, 2003): variance `(1/k + n_test/n_train) * s^2` with `k - 1` degrees of freedom, because CV folds share training rows (the naive `s^2/k` is too small); `n_test/n_train` is averaged over the run's actual folds | warning when a fold scores at or below the dummy or the interval includes zero; otherwise info, with the spread (std, coefficient of variation, fold lifts, interval) recorded | more data or repeated CV | Five folds give a wide interval, so a modest true lift on small data warns. The correction is a variance heuristic, not an exact test; it assumes fold differences are exchangeable, which forward-chaining time folds are not (early folds train on less data). |

## v1.1 changes (post-benchmark, not pre-registered)

The table above is v1.0, the version the pre-registered benchmark evaluated
([results.md](results.md)). v1.1 changes the rules below, each one derived from an error in
[error_analysis.md](error_analysis.md), so its numbers on the benchmark suites are
optimistic ([results_v11.md](results_v11.md)). `thresholds.toml` is byte-identical to
v1.0 (a test compares its hash with the `v1.0.0` tag); the new constants live in
`src/holdout/audit/thresholds_v11.toml`, layered on top, and both hashes are recorded in
every manifest. v1.0 behaviour = the v1.0 thresholds without the v1.1 layer.

| Check | v1.1 change | Why (error analysis) | New blind spot |
|---|---|---|---|
| **A3** | A near-unique column is ID-like only with an identifier *pattern*: a gap-free integer sequence, a uniform code shape, row-order correlation, or a key-like name (last name token in `key_name_tokens`: id, key, uuid, code, number, no, nbr, ref, ...). A near-unique integer measurement without one of these patterns is not ID-like (floats never were). The message claims "ordering encodes the outcome" only when row-order correlation is the evidence. | Section 3: `cpu_act` `freeswap` and `steel_plates_fault` `V3/V4/V8` (integer measurements) were called identifiers. | A real identifier with an anonymised name and no sequence or code shape (e.g. `col_1` on the anonymised Diabetes data) is no longer flagged. |
| **A4** | The fix asks for deduplication *before the split* only when the holdout overlap invalidates the holdout; otherwise it asks for deduplication of the development rows, which a plan can now do (`ModelPlan.deduplicate`). A plan that deduplicates is audited on the rows it is evaluated on. | Section 1: deduplication was a recommendation no plan could act on. | None new. The benchmark's duplicate traps overlap Holdout's own seal (about 17% of holdout rows), so they still invalidate the holdout and end the run: this change does not help them. |
| **A5** | An entity candidate must look like a key (a string or categorical column, or a numeric column with a key-like name) **and** have at least one entity-constant feature. | Section 3: `telco_churn` `number_vmail_messages` (a 0-52 count) was treated as an entity key on two clean tasks. | A numeric entity key with a neutral name (e.g. `x17`) is no longer tested. |
| **A11** | Also runs on the **goal** at intake (offline runs too). A causal question becomes a goal-level finding; the report carries a code-enforced decline: "This analysis is predictive: it cannot establish whether X affects Y, and no causal conclusion is drawn." | Section 1: a causal goal was answered without a decline whenever the prose avoided causal phrasing; offline runs never checked the goal. | The same lexicon, so a causal question phrased outside it ("is X responsible for Y?") is missed. |

**Data findings.** Before the planner, v1.1 audits a probe plan (every usable column, the
default model) on the raw development rows; the warning-or-critical flags of A1-A6 and A8
(and the goal's A11) become findings F1..Fn that persist for the run. The planner must
answer each one (`findings_handled`: action and reason); code decides the outcome and the
report lists every finding in "Problems found and how they were handled". A critical entity
or time finding is resolved only by a group or time split (or `--entities known`):
dropping the column re-asserts it at critical in every audit round, so the holdout-integrity
rule still applies ([design.md](design.md#v11-post-benchmark-fixes)).

## Severity calibration notes

- **Sampling.** Expensive checks use at most 20,000 development rows (whole groups for group
  splits and group candidates, every k-th row in time order for time splits, stratified for
  classification) and at most 200 features (the strongest by a univariate association on
  development rows, so a leaky column is not cut). Every flag's evidence records the sampling.
- **Noise.** A5 and A6 compare two CV scores; on small data with a weak model their
  difference is noisy (on clean classification twins: sd ~0.16 of the lift with a true drop
  of zero). The reference is re-run under a second shuffle and a drop must exceed 3x that
  shuffle-to-shuffle difference.
- **Planted versus clean.** Every check is tested on a planted case (it must fire at the
  expected severity) and on a clean twin (nothing above info), across 5 seeds; see
  `bench/traps/README.md` for the traps and their minimum expected severities.
